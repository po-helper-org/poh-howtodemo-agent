# Без result_type активность приезжала голым dict, а упавший агент выглядел проваленной приёмкой

## Ситуация

Первый живой прогон. В воркфлоу падало `'dict' object has no attribute 'verdict'`
(`workflow.py:36`): активность зовётся именем-строкой, аннотаций в имени нет, и конвертер
Temporal не знает, во что десериализовать результат. Воркфлоу зациклился на повторной
активации, отчёт не опубликовался вовсе. Рядом второй дефект: `finally` инициализировал
вердикт значением `V_FAILED`, и задача получала `demo:failed` при любом сбое самого агента.
Оба дефекта тесты не ловили.

## Причина

Тестовая подделка `_call` возвращала уже готовый `RunReport` — тот же класс слепоты, что
незадолго до этого был у провайдера токена: подделка добрее реальности. Метка же была одна
на два разных повода: «сценарий не пройден» и «агент сломался» не были разделены, и человека
метка посылала чинить продукт там, где чинить надо было агента.

## Решение

- `result_type=` на каждом типизированном вызове активности — идиома соседнего агента.
- Новый тест проверяет не поведение, а сам факт передачи `result_type` — иначе подделка
  снова всё скроет.
- При сорвавшемся прогоне вердикт пуст, ставится только метка `failed:howtodemo`, метки
  `demo:*` нет вовсе. `demo:failed` означает «чинить продукт», `failed:howtodemo` —
  «чинить агента»; это разные новости для разных людей.
- Метка запуска снимается во всех ветках.

83 теста (+4).

## Как проверить

Живой прогон с уроненной активностью: задача получает метку сбоя агента, `demo:failed` нет,
отчёт опубликован. `pytest -q`.

## Уроки

Подделка, отдающая готовый объект результата, прячет проблемы десериализации: для протоколов
с типизацией результатов держи тест на наличие `result_type`. И разделяй новости — «проверяемое
не прошло» и «проверяющий сломался» адресованы разным людям, у них разные метки.
