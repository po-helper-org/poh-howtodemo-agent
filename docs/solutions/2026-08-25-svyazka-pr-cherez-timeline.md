# Половина механизма была выложена и ни разу не работала — вебхук PR не слушался, номер PR был всегда нулём

## Ситуация

Стенд поднимается из SHA головы PR, а `pr_number` в прогоне всегда был нулём: вебхук событий
`pull_request` не слушается вовсе. Без PR нет SHA, без SHA нет стенда, без стенда не исполняется
ни один HTTP-шаг — выложенная половина механизма не работала ни разу. Ни один из 97 тестов
этого не показывал.

## Причина

Номер PR ожидался из внешнего события, на которое никто не был подписан. Прогон получал
по умолчанию ноль и честно считал, что PR у задачи нет — и это ничем не отличалось от
реального отсутствия PR.

## Решение

- `linked_pull` спрашивает GitHub сам — Timeline API, события `cross-referenced` (тот же
  приём, что у списка связанных PR у соседнего агента).
- Кросс-ссылка означает любое упоминание, а не «этот PR делает эту задачу», поэтому выбор
  вынесен в чистую функцию `pick_pull(events, issue)` и проверяется без сети:
  предпочитаем PR с закрывающим ключевым словом на наш номер в теле, из остальных — самый
  свежий открытый, закрытые не берём вовсе — приёмка идёт по живому PR.
- Явно переданный номер не перепроверяется: он пришёл от того, кто знает больше.

## Как проверить

Прогон живого цикла отладки против настоящего GitHub: в журнале `[live] PR задачи: <номер>`,
SHA головы, контракт из того же SHA. `pytest -q` — выбор PR на событиях без сети.

## Уроки

Внешний идентификатор, который приходит «откуда-то снаружи», без подписки на это «откуда-то» —
всегда дефолтное значение, неотличимое от нуля. Проверяй связку на живом прогоне до выкладки:
подделки и юнит-тесты путь «событие → идентификатор» не видят, если события нет. Наличие
упоминания — не доказательство связи; выбор из кросс-ссылок — отдельная проверяемая логика,
а не «первая попавшаяся».
