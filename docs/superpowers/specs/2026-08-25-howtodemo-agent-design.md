# HowToDemo-Agent — дизайн

Дата: 2026-08-25. Статус: согласован, к реализации.

## Задача

В контуре производства HowToDemo — объявленная граница MVP: «Нет HowToDemo — нет
критерия „готово“» (`poh-demo-checkout/CLAUDE.md`). Правило записано в трёх местах
и **не подкреплено ни одной строкой исполняемого кода**: парсера блока в контуре
нет, ни один потребитель сценарий не читает, проверка готовности сводится к
регрессионным HTTP-ассертам `.delivery/checks.json`, которые пишутся от кода, а
не от сценария.

Следствие для человека: агент, доделав работу, либо перепроверяет себя сам по
тому же тексту, который сам же и интерпретировал, либо не перепроверяет вовсе.
Отчёта нет или он не воспроизводим.

HowToDemo-Agent закрывает разрыв. Его единственная задача — **зафиксировать
исходный сценарий приёмки, автономно пройти его и доложить, что готово и что не
соответствует, с доказательствами**.

## Зона ответственности

Агент **не** пишет код, **не** мержит, **не** выкатывает и **не** решает судьбу
задачи. Он собирает факты и выносит вердикт по сценарию. Всё остальное —
чужая зона: разработка у OpenHands, релиз у Delivery-Agent.

## Уровень: базовый механизм

Этот репозиторий — **шаблон механизма**, не операционный экземпляр. Целевой
репозиторий, Issue и PR приходят параметрами прогона; контракт окружения берётся
из `.delivery/checks.json` целевого репозитория; сценарий — из его Issue.
Продуктовой специфики в коде нет.

Персонализация под конкретный продукт живёт в отдельном репозитории с суффиксом
(`poh-howtodemo-agent-DEMO` для `poh-demo-checkout`): настройки прогона, фикстуры
сценариев, всё верное только для одного продукта. Механизм он подключает пакетом,
а не форкает. Пока такой надобности нет: срез 1 гоняется на демо-репозитории
параметрами, без своего репозитория.

## Что установлено по коду

Дизайн опирается на факты, снятые с чистых состояний репозиториев 2026-08-25
(`poh-issue-agents@513e692`, `poh-delivery-agent@20b74e7`,
`poh-demo-checkout@3d6a74c`) и на живые замеры стенда. Пять фактов определяют
форму решения.

**Contents API не умеет бинарные файлы.** `github_client.put_file` типизирован
`content: str` и делает `content.encode("utf-8")`; то же в `create_pr_with_files`.
Функции с параметром `bytes` в клиенте нет, загрузки вложений нет, публичных
raw-ссылок никто не собирает. Скриншоты через этот путь не пройдут.

**Вебхук не обрабатывает событие `pull_request`.** Обрабатываются ровно два типа:
`issues` и `issue_comment`. Внешний вход один — `POST /agent-event` с HMAC-подписью.
Старт «PR открылся, проверь демо» неоткуда взять как событие GitHub.

**Фаза под демо-проверку уже объявлена и мертва.** `testing` присутствует в
`shared/lifecycle.py` вместе с переходами, но в код не входит ни одним переходом —
как и `released`. Заводить новую фазу не требуется.

**После релиза докладывать в Issue некому.** `IssueLifecycle` завершается на фазе
`merged`; к моменту работы Delivery-Agent живого цикла нет.

**Памяти под браузер на стенде нет.** Замер: свободно 975 МБ, свопа ноль, лимитов
памяти у контейнеров контура нет ни одного. Крупнейший потребитель на хосте —
чужой прод (2.5 ГБ). Playwright, `claude -p` (356 МБ) и раннер OpenHands в сумме
выбирают остаток, и жертву OOM ядро выберет само.

Два факта упрощают задачу.

**Сценарий де-факто неизменяем.** Тело Issue код контура не переписывает нигде
(`update_issue_body` вызывается только по новосозданным SubIssue); комментарии
append-only — во всём `worker/` два `requests.patch`, ни одного на
`/issues/comments/`. Проверено на живых данных: 0 правок тела на 100 Issue.
Значит якорь — **указатель с хэшем**, а не копия.

**Шаги сценария по исполнимости расходятся полярно.** Тело `poh-demo-checkout#29`
содержит `curl` и строку `Ожидаемо: {...}` — исполнимо один в один. Письмо БФТ на
`#41` описывает шесть экранов оформления заказа у сервиса, который является чистым
JSON-API без единой строки HTML. Неисполнимый шаг — штатный исход, а не отказ.

## Архитектура

Отдельный репозиторий, отдельный релизный цикл. В Harness подключается **модулем**:
пакет ставится в образ воркера пином на полный SHA, регистрируется отдельным
`Worker` на очереди Temporal `howtodemo`. Обратной зависимости нет — `poh_howtodemo`
не импортирует из Harness ничего, связь только через порты-протоколы и вызов
активностей по имени-строке.

```
poh_howtodemo/
  model.py       Scenario, Anchor, Step, Evidence, StepResult, Verdict
  anchor.py      поиск и фиксация сценария указателем с хэшем
  plan.py        сценарий → plan.json, валидация плана
  execute.py     диспетчер шага по kind, без ввода-вывода
  collectors/    http | cli | logs | browser — сбор доказательств
  env.py         эфемерный стенд из произвольного SHA
  verdict.py     чистый код: passed/failed/unmapped
  render.py      отчёт «Что готово / Что не соответствует»
  publish.py     git-пуш улик в ветку howtodemo/issue-<n>
  ports.py       протоколы GitHub, Docker, LLM
  github.py      реализация GitHub-порта поверх REST
  activities.py  активности Temporal — весь ввод-вывод
  workflow.py    HowToDemoVerify
  integration.py TASK_QUEUE, WORKFLOWS, ACTIVITIES, install()
```

Граница по вводу-выводу жёсткая: `anchor`, `plan`, `execute`, `verdict`, `render`
— чистые, тестируются без сети и без докера. Всё касание внешнего мира живёт в
`collectors`, `env`, `github`, `publish` и вызывается только из `activities`.

## Поток

### Вход 1 — прогон на PR

Стартует **изнутри жизненного цикла**, не по вебхуку. Фаза `pr-open` паркуется в
`IssueLifecycle._phase_park`; туда врезка: Harness зовёт активность
`howtodemo_verify` на очереди `howtodemo`. Вердикт возвращается переходом
`pr-open → testing`, далее `testing → pr-review` при успехе либо
`testing → in-development` при провале.

Ручной вход — `/howtodemo` и метка `run:howtodemo`. Обе добавляются одной записью
в реестр `shared/commands._COMMANDS`; метки `run:`/`done:`/`failed:` выводятся из
реестра и попадут в каталог сами.

**Терминальный `finish_command_labels` обязателен во всех ветках выхода.**
Прецедент: `run:release` заводится каталогом и не снимается никем — поставленная
человеком метка висит вечно.

### Вход 2 — прогон после релиза

Активность на очереди `howtodemo`, которую зовёт `DeliveryRelease` после успешной
выкатки шага. Отчёт идёт в **тело GitHub Release и в PR** — в Issue писать некому,
цикл завершён на `merged`. Требует правки `poh-delivery-agent` и нового пина;
согласуется отдельным PR туда.

### Шаг 1. Якорь

`anchor.py` ищет сценарий по приоритету:

1. раздел `## HowToDemo` в теле Issue;
2. блок `**How to demo:**` первого письма БФТ (редакция 1 — та, у которой нет
   строки `_Редакция N — с учётом замечаний…_`);
3. ничего.

Фиксирует указатель: `{issue, source: body|comment, comment_id?, sha256, taken_at}`.
Копии текста не хранит — источник неизменяем. Дальше читает по указателю и сверяет
хэш; расхождение даёт строку отчёта «сценарий менялся после фиксации» с диффом,
прогон продолжается по зафиксированной редакции.

Сценария нет ни в одном месте → метка `demo:no-scenario`, комментарий «критерия
готовности нет», выход. Исход частый и штатный: раздел присутствует в 9 Issue из
102 по замеру демо-репозитория.

Форма блока в контуре не одна (`**How to demo:**`, `How to demo:`, `### How to demo`,
`## HowToDemo`), константы-маркера нет. Парсер знает все четыре и нормализует.

### Шаг 2. План

Один вызов модели: текст шагов → `plan.json`, коммитится рядом с якорем.

```json
{ "n": 3,
  "text": "Отправить запрос GET /healthz, увидеть 200 и поле status=ok",
  "action": { "kind": "http", "method": "GET", "path": "/healthz" },
  "expect": { "kind": "json_subset", "value": { "status": "ok" } },
  "evidence": ["response", "service_log"],
  "source": "Issue #12, шаг 3" }
```

`kind`: `http` | `cli` | `browser` | `unmapped`.

`unmapped` — шаг, который не превращается в действие («проверяю входящее письмо»).
Он **не проваливает прогон**: даёт `demo:partial` и отдельную секцию «требует
человека». Это честный ответ, а не отказ.

Повторный прогон переиспользует план; пересборка — только явной командой. Прогоны
воспроизводимы, провал читается как «шаг 3 не исполнился», а не как молчание.

### Шаг 3. Окружение

`env.py` поднимает проверяемое состояние из произвольного SHA. Логика заимствована
у `poh_delivery.prod._materialize` (git init → remote с токеном → `fetch --depth 1
origin <sha>` → checkout) — она к «после мержа» не привязана и берёт head-SHA
открытой ветки так же, как merged.

Три обязательных отличия от прод-контура Delivery:

- **своё имя контейнера** `poh-howtodemo-<owner>__<repo>-<issue>`. Имя прод-контура
  зафиксировано модульной константой, а подъём начинается с `docker rm -f` — стенд
  с тем же именем снёс бы живой прод;
- **`--rm` вместо `--restart unless-stopped`** и явное гашение в `finally`:
  эфемерный стенд обязан умирать. В `ProdPort` метода `stop` нет вовсе;
- **гашение по таймауту** — осиротевший контейнер снимается по имени перед стартом,
  как это делает `_reap_runner`.

Контракт сервиса берётся из `.delivery/checks.json` целевого репозитория
(`service.start`, `port`, `image`, `health_path`). Второй формат не заводится.
Файла нет → шаги, требующие сервиса, помечаются `blocked`, отчёт говорит об этом
прямо; прогон не падает.

### Шаг 4. Доказательства

`collectors/http.py` — запрос и ответ целиком. `collectors/cli.py` — команда, код
возврата, stdout/stderr. `collectors/logs.py` — `docker logs` контейнера стенда за
временное окно шага; обёртки над `docker logs` в контуре нет ни одной, эта будет
первой. Возможность подтверждена живьём: воркер работает от root с прокинутым
`/var/run/docker.sock`. `collectors/browser.py` — срез 3, см. ниже.

Каждая улика — файл в `evidence/step-<n>/` рабочего каталога на томе
`poh-dev-workspace`, с меткой времени.

Инфра-логи первой версии — только `docker logs` контейнеров контура. Состояние
Temporal программно не читает никто (`describe`, `fetch_history`, `list_workflows`
— ноль вхождений в проде), а `SENTRY_TOKEN` на стенде не задан, и без него чтение
Sentry возвращает пустой список неотличимо от «ошибок нет». Оба источника — не
первый срез.

### Шаг 5. Публикация улик

`publish.py` делает **свой git-пуш** из рабочего каталога в ветку
`howtodemo/issue-<n>` — по образцу `github_client.publish_worktree`, но без
открытия PR. Contents API не используется: он бинарные файлы не умеет и не будет.
Отчёт ссылается на файлы ветки.

### Шаг 6. Вердикт

Считает **код**, не модель. Шаг `passed` только если: действие исполнилось без
ошибки, `expect` совпал и улики собраны. Модель пишет исключительно
человекочитаемый разбор.

Правило не теоретическое: в контуре уже есть ровно этот дефект — пайплайн БФТ
проверяет артефакт на существование, а вердикт стадии пишет сама же модель.
Повторять нельзя.

Итог прогона: все `passed` и `unmapped` нет → `demo:passed`; есть `unmapped` или
`blocked` → `demo:partial`; есть `failed` → `demo:failed`.

### Шаг 7. Отчёт

```
## HowToDemo — прогон на PR #45 (ветка feature/12-cart, 3a1f0c2)
Сценарий зафиксирован 2026-08-25: тело Issue #12, sha256 a1b2c3…

### Что готово
✅ 1. GET /healthz → 200, status=ok            [ответ] [лог сервиса]
✅ 2. POST /quote с двумя позициями → 2000 ₽    [ответ]

### Что не соответствует
❌ 3. Ожидался итог 2300, пришло 2000           [ответ] [лог сервиса]
      Источник требования: Issue #12, шаг 3
⚠️ 5. «Проверяю входящее письмо» — не проверяется автоматически

### Улики
ветка howtodemo/issue-12, каталог evidence/
```

Отчёт несёт машиночитаемый маркер-строку — по образцу того, как Delivery читает
вердикт круга правок из комментария соседнего агента.

## Действия по вердикту

- **Метка** `demo:passed` / `demo:failed` / `demo:partial` / `demo:no-scenario`.
  Агент не трогает `phase:*` напрямую — фазу двигает через `/agent-event`.
- **Возврат в доработку** при `demo:failed`: своя постановка (аналог
  `pr_closing.build_task`) и мостовая активность на очереди `issue-lifecycle` по
  образцу `delivery_review_round`. Новый механизм запуска агента не нужен —
  `run_pr_fix_round` уже делает ровно это. **Потолок кругов — один**, повтор
  инициирует человек: у активности с недетерминированной дорогой работой повтор
  означает повтор всей работы.
- **SubIssue** на каждый пункт `❌` с `root-issue: #N` и `origin:agent`. На `⚠️` —
  нет: неисполнимый шаг это не дефект продукта.
- **Блокировка релиза**: Delivery не берёт PR без `demo:passed`. Правка
  `poh_delivery/rules.py`, отдельный PR в чужой репозиторий.

## Решения по трём развилкам

**Браузер — срез 3, и только после замера.** Перед реализацией обязателен разовый
`docker run` образа Playwright с `docker stats` на стенде: RSS headless-Chromium там
не измерен. На время браузерного прогона модуль гасит **свои** сервисы —
Repowise (778 МБ) и `harness-memory-api` (52 МБ), оба деградируют штатно, — и
поднимает обратно в `finally`. Чужие контейнеры не трогаются никогда. Если замер
покажет, что не помещается и так, браузерная ветка уезжает с этого хоста.

**Скриншоты — свой git-пуш внутри модуля.** Альтернатива (`put_binary` в
`github_client`) требует правки Harness и лишнего круга выкладки ради общего блага,
которое сейчас нужно одному потребителю. Принцип модуля — не иметь обратной
зависимости — весомее.

**Фаза — оживить объявленную `testing`.** Она семантически ровно эта проверка и
уже описана в модели с переходами. Расхождение: в переходе `testing → in-development`
инициатором объявлен `HUMAN`, а двигать будет агент. `transition()` инициатора не
проверяет, но модель придётся поправить явно, а не молча.

## Тестирование

Подделки портов, без сети и без докера — по образцу `poh-delivery-agent/tests`.
Обязательные случаи:

- якорь: все четыре формы блока; отсутствие сценария; расхождение хэша;
- план: `unmapped` не проваливает прогон; невалидный план отвергается;
- вердикт: успех только при совпадении `expect` **и** наличии улик; отсутствие
  улик при совпавшем `expect` — не `passed`;
- окружение: имя контейнера никогда не совпадает с прод-контуром Delivery;
  гашение выполняется и при исключении;
- метки: `finish_command_labels` вызывается во всех ветках выхода, включая
  `no-scenario` и падение.

Живой прогон первого среза — на `poh-demo-checkout`: чистый JSON-API без UI,
формат «`curl` + `Ожидаемо:`» уже прижился в его Issue.

## Порядок работ

**Срез 1.** Якорь, план, `http`/`cli`, вердикт, отчёт, метки, публикация улик.
Проверяемо живьём без единого байта браузера.
**Срез 2.** Эфемерный стенд из ветки PR, логи сервиса, врезка в фазу `testing`.
**Срез 3.** Браузер — после замера памяти.
**Срез 4.** Возврат в доработку, SubIssue, блокировка релиза.

## Найдено попутно — вне этой работы

Отдельными Issue, не в этом репозитории:

1. **Репозиторий без `.delivery/checks.json` откатывает каждый свой PR.**
   Документация трижды обещает «релиз пойдёт, подтверждать поведение нечем»;
   код возвращает `DeployResult(ok=False)` из-за пустого `service.start` и уходит
   в откат. Тестами не покрыто — стаб всегда отдаёт непустой `service`.
2. **Прод демо-репозитория красный по собственному контракту**: `checks.json` ждёт
   от `/healthz` поле `ok`, сервис отдаёт `status`. Контракт отстал от кода на пять
   коммитов.
3. **LLM-слой теряет токен `json`**: `application/json` → `application/`,
   `package.json` → `package.` — в том числе в колонке, объявленной дословной
   цитатой, и в заголовках SubIssue.
4. **`run:release` не снимается никем** — метка команды висит вечно.
5. **У контейнеров контура нет лимитов памяти**, при том что собственное правило
   организации это требует.
