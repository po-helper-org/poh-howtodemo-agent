# poh-howtodemo-agent

**HowToDemo-Agent — приёмщик контура производства.**

Миссия и зона ответственности: зафиксировать исходный сценарий приёмки, автономно
пройти его после того, как работа доделана, и доложить с доказательствами — что
готово и что не соответствует.

Постановка и разбор — [#1](https://github.com/po-helper-org/poh-howtodemo-agent/issues/1).
Дизайн — [`docs/superpowers/specs/2026-08-25-howtodemo-agent-design.md`](docs/superpowers/specs/2026-08-25-howtodemo-agent-design.md).

## Это базовый шаблон механизма

Репозиторий не привязан ни к одному целевому проекту. Репозиторий, Issue и PR
приходят параметрами прогона; контракт окружения агент читает из
`.delivery/checks.json` **целевого** репозитория; сценарий — из тела его Issue
либо из письма БФТ. Ничего специфичного для конкретного продукта в коде нет и
быть не должно.

Персонализированный операционный экземпляр под конкретный репозиторий — отдельный
репозиторий с суффиксом (`poh-howtodemo-agent-DEMO` для `poh-demo-checkout`):
там живут настройки прогона, фикстуры сценариев и всё, что верно только для
одного продукта. Механизм он подключает пакетом, а не форкает.

## Зачем

HowToDemo объявлен границей MVP: «Нет HowToDemo — нет критерия „готово“». Правило
записано в трёх местах и не подкреплено ни одной строкой исполняемого кода —
парсера блока в контуре нет, ни один потребитель сценарий не читает. Готовность
проверяется регрессионными HTTP-ассертами, которые пишутся от кода, а не от
сценария.

Агент, доделавший работу, перепроверяет себя по тому же тексту, который сам же и
истолковал. Этот агент проверяет его снаружи и по зафиксированной редакции.

## Что делает

1. **Фиксирует сценарий** — указателем с хэшем на тело Issue либо на первое письмо
   БФТ. Копию не хранит: источник неизменяем. Сценарий подменили после фиксации —
   это отдельная строка отчёта, а не молчание.
2. **Собирает план** — один вызов модели превращает шаги в действия. Шаг, который
   в действие не превращается, помечается `unmapped` и уходит в секцию «требует
   человека». Это честный результат, а не отказ.
3. **Поднимает окружение** — эфемерный стенд из произвольного SHA: и из ветки
   открытого PR, и из выкаченного состояния. Контракт сервиса берёт из
   `.delivery/checks.json` целевого репозитория, второго формата не заводит.
4. **Проходит шаги и собирает улики** — ответы сервиса, вывод команд, логи
   контейнера, скриншоты. Улики уезжают git-пушем в ветку `howtodemo/issue-<n>`.
5. **Выносит вердикт** — считает **код**, не модель. Шаг зачтён только когда
   действие исполнилось, ожидание совпало и улики собраны.
6. **Публикует отчёт** — «Что готово / Что не соответствует», со ссылкой на улики
   и на источник каждого требования.

## Зона ответственности

Агент не пишет код, не мержит, не выкатывает и не решает судьбу задачи. Он
собирает факты и выносит вердикт по сценарию. Разработка — у OpenHands, релиз — у
[Delivery-Agent](https://github.com/po-helper-org/poh-delivery-agent).

## Как это устроено

Отдельный репозиторий, отдельный релизный цикл. В Harness
(`po-helper-org/poh-issue-agents`) подключается **модулем**: пакет ставится в образ
воркера, регистрируется отдельным `Worker` на очереди Temporal `howtodemo`.
Обратной зависимости нет — `poh_howtodemo` не импортирует из Harness ничего.

```
poh_howtodemo/
  model.py       факты и решения (dataclass'ы, ездят через Temporal)
  anchor.py      поиск и фиксация сценария указателем с хэшем
  plan.py        сценарий → машиночитаемый план
  checks.py      контракт окружения из .delivery/checks.json целевого репо
  env.py         эфемерный стенд из произвольного SHA
  collectors/    сбор доказательств: http | cli | logs (browser — впереди)
  verdict.py     чистый код: passed / failed / skipped / blocked
  render.py      отчёт «Что готово / Что не соответствует»
  publish.py     git-пуш улик в ветку howtodemo/issue-<n>
  run.py         прогон целиком, всё внешнее приходит параметрами
  ports.py       протоколы GitHub, модели, оболочки
  github.py      реализация GitHub-порта поверх REST
  activities.py  активности Temporal — весь ввод-вывод
  workflow.py    HowToDemoVerify
  integration.py точка подключения к Harness
```

Вердикт считает код, а не модель. Иначе разбор неудачной приёмки упирается в
«модель так решила», а провал становится неотличим от успеха — этот класс отказов
в контуре уже встречался и стоил дороже всех прочих.

## Состояние

**Срез 1** — якорь, план, `http`/`cli`, вердикт, отчёт, публикация улик. Влит.
**Срез 2** — эфемерный стенд из произвольного SHA, контракт окружения из
целевого репозитория, логи сервиса за окно шага. Влит.
**Срез 3** — агент сам находит PR задачи (без него стенд не поднимался никогда),
источник требования считает код, команда без рабочей копии помечается `blocked`,
отчёт называет причину отсутствия окружения. В работе.

Впереди: цепочные шаги (утверждение о ответе предыдущего шага); браузер — после
замера памяти на стенде; возврат в доработку, SubIssue на несоответствия,
блокировка релиза. Врезка в фазу `testing` живёт в `poh-issue-agents`;
регистрация `/howtodemo` там уже сделана.

Ядро (`anchor`, `plan`, `checks`, `verdict`, `render`, `run`) чистое: тесты
гоняются без сети, без докера и без Temporal.

```bash
python -m venv .venv && .venv/bin/pip install -e ".[dev]" pytest-asyncio
.venv/bin/pytest -q
```

## Отладка: живой прогон с ноутбука

Круг отладки через контур стоит тридцать с лишним минут — мерж, пин, сборка
образа, ожидание окна между прогонами агента разработки, `up -d`, чтение логов.
`scripts/live.py` гоняет тот же `run.verify` с теми же реализациями: настоящий
GitHub по токену `gh`, настоящий докер, настоящая модель. Не участвуют только
Temporal и воркер контура.

```bash
# готовый план вместо вызова модели, без окружения — быстрее всего
scripts/live.py --repo po-helper-org/poh-demo-checkout --issue 100 \
                --plan plan.json --no-stand

# полный прогон: агент сам найдёт PR, поднимет стенд, пройдёт шаги
scripts/live.py --repo po-helper-org/poh-demo-checkout --issue 147
```

По умолчанию скрипт **ничего не пишет наружу**: ни комментария, ни меток, ни
ветки с уликами. Отчёт печатается в stdout, улики лежат в `.live/evidence`.
Публикация — явным `--push`.

Для прогона со стендом нужен запущенный докер: стенд поднимается контейнером и
публикует порт наружу, потому что с ноутбука имя контейнера не резолвится.
